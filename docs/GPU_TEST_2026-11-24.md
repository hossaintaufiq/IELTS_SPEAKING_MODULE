# First live GPU test, 2026-11-24

First time the service ran on a real GPU. Goal: see that it works end to end on the cheapest 24 GB card, then push the number of simultaneous tests until it breaks and find the stable limit.

## Setup

| | |
|---|---|
| Card | 1x RTX 3090, 24 GB, driver 615.71 (vast.ai, $0.242/h; 12 CPU cores, 31 GB RAM) |
| Software | Pipecat 0.0.108, faster-whisper 1.2.1 (`large-v3-turbo` for answers, `small.en` for live captions), Kokoro (onnxruntime-gpu 1.22), vLLM 0.34 with Qwen2.5-7B-Instruct-AWQ (59% of GPU memory) |
| Service | `/v1/session` with an API key, `MAX_SESSIONS=200` (no limit), captions on (defaults) |
| Load | `eval/load_test.py`, run on the same box (no network in the numbers). Each simulated candidate speaks 6 scripted answers (voiced by Kokoro). Candidates start 1 s apart |
| Verdict rule | PASS when p95 reply delay is within 1 s of the 1-session baseline (4.98 s) and nobody is refused, errors, or gets no reply |

Raw reports: `docs/gpu_test_2026-11-24/` (`base.json` is 1 session, `nN.json` is N sessions, plus the two ramp logs).

## What we found

1. **It works on a real GPU.** One full test, start to finish, through the new `/v1/session` API with a key. This was the first time any of the service code ran on a GPU.
2. **Comfortable limit: 9 tests at once** on one RTX 3090 (reply delay stays within 1 s of the single-test number).
3. **Error-free limit: about 26.** Between 12 and 26 nothing fails, but replies are about 1.5-2 s slower than a single test.
4. **Hard ceiling: about 29.** At 29 the delay doubles and GPU memory is at 23.6 of 24 GB. At 32 and above, the examiner stops answering about half of the answers. The limit is the 24 GB card (the LLM takes 59% of memory), not the service code.
5. **Recommended setting for this card:** `MAX_SESSIONS` about 9 for a good experience, and never above about 20. The service already refuses with close code 1013 when full, so students are told to wait instead of getting a stalled examiner.
6. **Problem found: GPU memory is not freed after an overload.** After the 29/32/40 runs memory stayed at 23 GB with zero tests running, and a single test was slower (6.45 s instead of 4.98 s). Restarting the web service brought memory back to 17 GB. The service needs a fix (or an automatic recycle) so that one overload cannot degrade the next students.
7. **Under overload the examiner goes quiet instead of refusing.** Past the limit the sessions stay connected but get no reply. A safer behaviour is to refuse or ask the student to wait while the GPU is overloaded. Worth adding a guard based on measured reply delay, not only on the number of sessions.
8. **The load test is the same-box best case.** A real browser adds network time, and real voices are harder than synthetic ones, so real limits will be a bit lower. Nothing here used real candidate audio.

## Things fixed on the way (not yet in the tests above)

- `deploy/vast/upload.sh` now takes `SSH_KEY=` for the key path.
- Files uploaded from Windows have CRLF line endings, which break the setup script on Linux (`set: pipefail: invalid option`). The fix used was `sed -i 's/\r$//'` on the box; the upload script should do that itself.
- vast.ai: the first rented machine had a broken port setup and never accepted SSH (destroyed). Offers also disappear within seconds, so renting needs a retry. The account's SSH key had to be attached to the instance with `attach ssh`.
